# Next.js migration: loading results (2026-11-21)

This compares the Next.js 16 build (`feat/nextjs` at bcaa073 plus the Task 14 header fix) with the Vite site on `main` at 8a815e4. Both run on the same machine:

- **New site:** `next build`, then `next start -p 4300`, tested at `/`.
- **Old site:** `vite build --base=/portfolio/` with SSR prerender (`main`'s build script without its `tsc` step, which fails in a fresh `npm ci` worktree), then `vite preview`, tested at `/portfolio/`.

The Vercel preview does not exist yet (Task 13), so this is a local production run, not the CDN. Both servers gzip their responses, so the transferred KB below are gzip sizes for both sites.

Lighthouse 12 ran with mobile emulation, simulated throttling and the performance category only. Each config ran 5 times and the tables show the median.

## What is worse, and why

- **LCP (+1.3 to 1.5 s, simulated).** The LCP element is the same on both sites: the hero paragraph, which is in the static HTML. In the unthrottled trace the new site paints it earlier than the old one: observed LCP is about 2.29 s against 2.50 s. Only Lighthouse's simulated LCP is worse.

  The likely cause is that the render delay grows from 2.4 s to 3.9 s. In Lighthouse's simulation, the ten `async` Next.js scripts on `/` (209 KB gzip, against 141 KB of `type=module` scripts on the old site) run before the LCP paint.
- **JS bytes (+77 to 97 KB).** There are two reasons:
  - React 19 DOM and the Next.js runtime together are larger than the old React 18 and React Router vendor chunk.
  - `motion` is in the first load.

  The lazy three.js chunk is about the same size on both sites: 183 KB new, 191 KB old.
- **Total bytes (+116 to 135 KB).** On top of the JS:
  - The HTML grows from 13 to 28 KB because of the inline React Server Components payload.
  - About 23 KB of `?_rsc` prefetches come from `next/link` in the viewport.
- **First-load JS budget.** `/` is at 209 KB gzip against a budget of 140 KB.

## Possible follow-ups (not done here, outside Task 14's scope)

- Load `motion` through `LazyMotion` with `domAnimation` and use `m.*` components. That would save roughly 30 to 40 KB gzip on the first load.
- Lazy-load `ToastContainer` (react-toastify) on the first toast.
- Set `prefetch={false}` on the `next/link`s in the header and hero to drop the RSC prefetches on load.
- Re-measure on the Vercel preview, which serves Brotli and HTTP/2 from a CDN, once Task 13 is done.

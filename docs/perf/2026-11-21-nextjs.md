# Next.js migration: loading results (2026-11-21)

This compares the Next.js 16 build on `feat/nextjs` (e72491a, after the Task 14 optimisation commits) with the Vite site on `main` (8a815e4). Both run on the same machine:

- **New site:** `next build`, then `next start -p 4300`, tested at `/`.
- **Old site:** `vite build --base=/portfolio/` with SSR prerender (`main`'s build script without its `tsc` step, which fails in a fresh `npm ci` worktree), then `vite preview`, tested at `/portfolio/`.

Both servers gzip their responses. The Vercel preview does not exist yet (Task 13), so these are local production runs, not the CDN.

Lighthouse 12 ran with mobile emulation, simulated throttling and the performance category only. Each config has 5 runs, and the tables show the median.

**The old and new runs are interleaved (old, new, old, new, …) in one session.** On this machine TBT swings by several seconds between quiet and busy periods. An earlier pair of baselines, measured an hour apart, gave the old site's median TBT as 5751 ms in a busy period and 1044 ms in a quiet one. Only interleaved runs compare fairly.

## What each optimisation bought

First-load JS is the gzip size (level 9) of every `<script src>` in the prerendered HTML. The `noModule` polyfill chunk is excluded because modern browsers do not load it.

| Step | `/` first-load JS | `/projects` | `/cv/react-native` | Other effect |
|---|---|---|---|---|
| Before (Task 14 report) | 209.3 KB | 160.4 KB | 158.7 KB | — |
| 1. `LazyMotion` + `m.div` (`motion/react-m`); `domAnimation` in its own chunk | 179.8 KB | 171.4 KB | 169.7 KB | −29.5 KB on `/` (see note 1) |
| 2. `ToastContainer` moved into the lazy contact form | 174.1 KB | 165.7 KB | 164.0 KB | react-toastify leaves the first load |
| 3. `prefetch={false}` on cross-page links; section links skip prefetch on the home page | 174.1 KB | 165.7 KB | 164.1 KB | `/` no longer fetches 5 `?_rsc` payloads (about 23 KB) |
| 4. Bundle audit | — | — | — | Nothing worth changing (see below) |
| 5. Lazy poster frames under the project videos | 174.1 KB | — | — | −121 KB of JPEGs during load; total 598 → 478 KB; simulated LCP about −0.6 s |
| 6. `quality={90}` on the small thumbnails | — | — | — | Visual only |
| 7. tsconfig excludes `.next/dev` | — | — | — | tsc stays clean after `next dev` |

Note 1: in step 1, `/projects` and `/cv` grew by about 11 KB. Turbopack now puts the small `m`/`LazyMotion` core in a chunk shared by the layout. Before, the full `motion` lived only in the home page chunk, and the layout loaded just `MotionConfig`.

Lighthouse medians (WebGL off) at each stage were measured in different noise conditions, so only the interleaved final table above is comparable. Two single-variable experiments on the same build and in the same quiet period isolate what drives the simulated LCP:

|---|---|
| After steps 1–3, as built | about 4000 ms |
| Same build, `*.jpg` blocked (the change that became step 5) | 3302 / 3403 / 3386 ms |
| Same build, every `/_next/static/chunks/*.js` blocked | 2710 ms |

## First-load JS for `/`: 174.1 KB gzip against a 141 KB budget

| Chunk | gzip |
|---|---|
| React DOM 19 (including the RSC client) | 69.8 KB |
| Next.js client runtime (router, segment cache, `next/link`, `next/image`) | 45.2 KB |
| Turbopack runtime and Next bootstrap chunks | 16.7 KB |
| **Framework subtotal** | **131.7 KB** |
| motion core (`m`, `LazyMotion`, `MotionConfig`) | 10.3 KB |
| App client components (header, theme, wine loop, scrollbar, projects, hero, contact islands, Speed Insights) | 32.1 KB |

**The framework alone is 131.7 KB gzip.** Meeting the 141 KB budget, which was the old entry plus vendor, would leave about 9 KB for all client components. The old site paid about 42 KB gzip for React 18 DOM and had no router runtime of this size.

The source-map audit (`productionBrowserSourceMaps` in a throwaway build) found nothing else large:
- heroicons: 2.2 KB raw, already per-icon imports;
- `classnames`: 0.7 KB;
- `src/data/projects.ts`: 2.1 KB;
- the contact icons: 4.3 KB raw.

`optimizePackageImports` would not change these sizes measurably, so I did not add it.

## Why LCP, TBT and the score are still worse

1. **Script bytes in flight before first paint.** In Lantern's simulation every request that starts before the observed paint counts toward LCP. On `/` that is 12 Next.js scripts (174 KB gzip) against the old site's 2 module scripts (141 KB). Blocking all Next chunks drops simulated LCP to 2.71 s, below the old site's 2.97 s. The remaining +0.27 to +0.34 s is the framework's bytes.
2. **Main-thread work after paint (TBT, TTI).** In the interleaved WebGL-off runs, the React DOM chunk's bootup is 463–634 ms scripting, against 249–272 ms for the old vendor chunk, roughly twice as much. This is hydration through the RSC payload with React 19.
   - The lazily loaded three.js chunk evaluates in 113–124 ms against 23–30 ms for the old chunk. The same wine-button loop loads it, and `loop.ts` and `renderer.ts` are off-limits.
   - The prerendered HTML is 28 KB gzip against 13 KB. It carries the inline RSC payload: 75 K characters and 213 client element references, 101 of them the `<T>` translation component.
3. **WebGL on.** TBT, SI and TTI are dominated by SwiftShader running the shaders and swing several seconds per run on both sites. That library code is untouched, but the R3F 9 and three 0.187 upgrades and the scheduler may cost more per frame. I did not profile it.

## Possible next steps (not done; beyond the brief's small-fix scope)

- **Render translations on the server.** A server-side `T` with a request-scoped locale, the pattern next-intl uses, would remove the 101 client `T` references from the RSC payload and from hydration. This is a refactor across every section, and the component tests would need a new harness.
- **Replace `Reveal`'s motion with a CSS transition plus an IntersectionObserver.** That saves the remaining 10.3 KB of motion. It is visually the same (0.5 s `ease-out`, 12 px), but it replaces the library that step 1 was asked to keep.
- **Profile the WebGL-on frame loop** on R3F 9 against the old R3F.
- **Re-measure on the Vercel preview** (Brotli, HTTP/2, CDN) after Task 13.

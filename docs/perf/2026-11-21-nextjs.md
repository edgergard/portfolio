# Next.js migration: loading results (2026-11-21)

This compares the Next.js 16 build on `feat/nextjs` (a54b473, after two optimisation rounds) with the Vite site on `main` (8a815e4). Both run on the same machine:

- **New site:** `next build` (Turbopack), then `next start -p 4300`, tested at `/`.
- **Old site:** `vite build --base=/portfolio/` with SSR prerender (`main`'s build script without its `tsc` step, which fails in a fresh `npm ci` worktree), then `vite preview`, tested at `/portfolio/`.

Both servers gzip their responses. The Vercel preview does not exist yet (Task 13), so these are local production runs, not the CDN.

Lighthouse 12 ran with mobile emulation, simulated throttling and the performance category only. Each config has 5 runs, and the tables show the median.

**The old and new runs are interleaved (old, new, old, new, …) in one session.** On this machine TBT swings by several seconds between quiet and busy periods. Two baselines of the old site measured an hour apart had a median TBT of 5751 ms and 1044 ms. Only interleaved runs compare fairly.

## What each optimisation bought

First-load JS is the gzip size (level 9) of every `<script src>` in the prerendered HTML. The `noModule` polyfill chunk is excluded because modern browsers do not load it.

|---|---|---|---|---|

| R1.1 `LazyMotion` + `m.div` | 179.8 KB | 171.4 KB | 169.7 KB | — |

| End of round 1 | 174.1 KB | | | score 69 → 63, LCP 2973 → 3242, TBT 1191 → 2461 |
| R2.1 `next build --webpack` (tried, **dropped**) | 174.4 KB | 177.9 KB | 177.8 KB | score 67 → 64, LCP 2970 → 3206; three.js chunks larger (88 + 101 KB gzip) and slower to evaluate (125–172 ms) |
| R2.2 server-side translations (tried, **dropped**) | 174.1 KB | 165.1 KB | 163.5 KB | score 70 → 64, LCP 2975 → 3245; hydration only about 5% cheaper |
| **R2.3 CSS + IntersectionObserver reveal; motion removed** | **157.8 KB** | **154.5 KB** | **152.8 KB** | **score 66 → 68, LCP 3001 → 2747** |

Notes on the two dropped steps:

- **R2.1 webpack.** It gave the same first load as Turbopack (174.4 vs 174.1 KB) and no Lighthouse gain. Its three.js output is larger.
- **R2.2 server-side translations.**
  - What it did: a `React.cache`-scoped request language, set in the layout and the pages, because Next renders the two in parallel.
  - Effect: client element references in the RSC payload went from 213 to 115, but the payload only shrank from 74.7 K to 74.1 K characters, because the strings move inline. React DOM bootup went from 463–634 to 424–701 ms.
  - It did not move the numbers, so I reverted it. The patch is kept outside the repo for reference.

## First-load JS for `/`: 157.8 KB gzip against a 141 KB budget

| Chunk | gzip |
|---|---|
| React DOM 19 (including the RSC client) | 69.8 KB |
| Next.js client runtime (router, segment cache, `next/link`, `next/image`) | 45.2 KB |
| Turbopack runtime and Next bootstrap chunks | 16.7 KB |
| **Framework subtotal** | **131.7 KB** |
| App client components (header, theme, wine loop, scrollbar, projects, hero, contact islands, Speed Insights, Reveal) | 26.1 KB |

**The framework alone is 131.7 KB gzip.** The old site's 141 KB entry plus vendor had React 18 DOM (about 42 KB) and no router runtime of this size. Getting under 141 KB would leave about 9 KB for every client component on the page. Even so, LCP and score now beat the old site, because the JS loads `async` after a faster first paint.

## What is still worse, and why

- **TBT (+0.46 s WebGL off, +1.0 s on) and JS bytes (+16 / +35 KB).**
  - Hydration: the React DOM chunk now boots in 382–454 ms (down from 463–634 ms before R2.3), against 252–317 ms for the old vendor chunk. That is React 19 hydrating through the RSC payload, about 75 K characters inline. The payload includes the whole dictionary passed to `I18nProvider` (about 10 KB per locale).
  - three.js: the lazily loaded chunk evaluates in 113–134 ms against 25–36 ms for the old chunk. The wine-button loop loads it in both sites, and `loop.ts` and `renderer.ts` are off-limits.
  - These are framework costs (React 19 plus the RSC payload) and protected-file costs, not a build defect: the build is production-minified, three.js is in one chunk, and `next build --webpack` was no better.
- **WebGL on.** TBT is dominated by SwiftShader running the shaders and swings by seconds on both sites.
